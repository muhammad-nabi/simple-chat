## Epic Summary

Epic 2 delivered a complete authentication system: user registration with first-user admin designation, login with rate limiting and timing-safe credential verification, session persistence with token rotation and reuse detection (emergency lockout), and server-side logout with single-device invalidation. ## What Went Well

1. **Identity extension decision was the right architectural call** — Story 2.1 deviated from the architecture spec (which called for custom User entity with direct bcrypt) by extending ASP.NET Core Identity instead. This gave us `UserManager`, password validation, and role management for free. The bcrypt hasher slotted in via `IPasswordHasher<ApplicationUser>` and the `IIdentityService` abstraction layer made the deviation invisible to the rest of the stack. Nabi confirmed this was the standout decision of the epic.

2. **Story-to-story deferred work resolution loop** — Each story explicitly resolved items from previous stories: 2.2 picked up CORS hardening and rate limiting from 2.1, 2.3 extracted `TokenConstants.cs` from 2.2's hardcoded expiry review finding, 2.4 wired up server-side logout deferred since 2.3. Every story spec had "Deferred Work Items Resolved" sections.

3. **"DO NOT Recreate" sections in story specs** — Explicit lists of existing services to reuse (`JwtTokenService`, `RedisSessionService`, `AuthService`, `Auth.cs` endpoints) prevented accidental duplication and saved real implementation time.

4. **Code review discipline held strong** — 29 findings across 4 stories, every one categorized as Patch or Defer. 19 security and correctness issues fixed in-story. Continues the pattern established in Epic 1.

5. **CQRS pattern consistency** — Command + Handler + Validator applied uniformly across Register, Login, RefreshToken, and Logout. Every story followed the same structure, making the codebase predictable.

6. **49 unit tests with zero regressions** — Test count grew from 26 (end of Epic 1) to 49, with every handler and validator fully covered. No test ever broke from a subsequent story's changes.

---

## Challenges

1. **Integration tests not fully green** — Identity's password validator rejects test passwords ("password123") with complexity rules. This was discovered in Story 2.2 and carried through Stories 2.3 and 2.4 without resolution. Root cause: `CustomWebApplicationFactory` doesn't relax password validator options for the test environment. One-line fix, but deferred across 3 stories.

2. **Security edge cases dominated reviews** — Timing side-channel for user enumeration (2.2), ProblemDetails leaking .NET default messages (2.2), URL matching using `includes()` instead of `endsWith()` (2.3), missing logging on token theft detection (2.3), in-flight refresh overwriting cleared session state after logout (2.4). These are subtle concurrency and security issues that require careful review.

3. **Hardcoded values kept surfacing** — The 7-day refresh token expiry was hardcoded in 4 locations before Story 2.3's review caught it and extracted `TokenConstants.cs`. Pattern: magic numbers introduced in one story, caught by review in the next.

4. **Deferred item count not formally tracked** — Epic 1 retro committed to tracking net debt per epic. Stories resolved deferred items effectively, but no formal count was maintained to compare debt growth vs. resolution.

---

## Key Insights

1. Extract constants immediately when introducing config values — don't wait for review to catch hardcoded duplicates
2. Auth code requires extra vigilance on concurrency and state transitions — timing, races, and state management are the primary attack surface
3. Test infrastructure issues should be fixed when discovered, not deferred indefinitely — carrying broken tests across stories erodes confidence
4. The story-to-story deferred work resolution loop is the strongest process artifact — continue and protect it

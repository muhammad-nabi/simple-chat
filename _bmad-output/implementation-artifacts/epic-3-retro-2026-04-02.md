## Successes

1. **Persist-first → SignalR broadcast architecture** — Rock-solid real-time messaging pipeline. Messages saved to DB before broadcasting, ensuring data integrity. Pattern extensible for Epic 4 group messaging.

2. **IMessageBroadcaster Clean Architecture abstraction** — Elegantly solved the layer boundary problem. Application layer publishes MediatR notifications, Web layer broadcasts via SignalR, neither knows about the other. Reusable pattern.

3. **Design token system** — `_tokens.scss` and `_mixins.scss` from Story 3.4 accelerated all subsequent UI work. Consistent spacing, colors, breakpoints with no guessing. Stories 3.5-3.9 all built on this foundation.

4. **100% Epic 2 retro follow-through** — All 4 action items completed. Test infrastructure fixes paid dividends across the entire epic. Proved the retro-to-action-to-results loop works.

5. **Story-to-story dev notes** — "Existing Infrastructure to Reuse" and "Critical Implementation Patterns" sections prevented re-discovery and duplication. Each story started with full context.

6. **Testing discipline** — 0 → 247 frontend tests, 34 new backend unit tests, 16 new integration tests. Every story shipped with comprehensive test coverage.

7. **Cursor-based pagination pattern** — `Id < @cursor ORDER BY Id DESC, Take(limit+1)` for HasMore detection. Elegant, performant, reused cleanly in Story 3.6's infinite scroll.

8. **Mobile-first responsive approach** — Three breakpoints, clean panel switching, no external dependencies like @angular/cdk. CSS Grid + matchMedia listeners.

---

## Challenges

1. **Race conditions in async frontend code** — Same bug category in Stories 3.6, 3.7, 3.8: stale closures, missing in-flight cancellation, fast user action races, SignalR echo deduplication. All caught in review but not in initial implementation.

2. **Frontend review patch volume significantly higher than backend** — Stories 3.5-3.8 averaged 6-8 patches each vs 2-3 for backend stories. Root cause: backend patterns were mature from Epic 2; frontend patterns were being invented during Epic 3.

3. **~12 deferred items accumulated** — Some low-priority (100vh mobile overflow, RelativeTimePipe time-dependence), but others carry real risk (DisplayName null crash, N+1 unread queries, no conversations pagination).

4. **Pre-existing test failures carried forward** — `app.component.spec.ts` 2 test failures noted in Story 3.3, never fixed. Carried through 7 stories. Erodes CI trust.

5. **Frontend pattern maturity gap** — Backend had 2 epics of pattern establishment (CQRS, FluentValidation, Clean Architecture layers). Frontend was starting from scratch. By Story 3.9, patterns were stable.

---

## Key Insights

1. **Fixing infrastructure debt before the epic starts pays massive dividends** — Proven by Epic 2 retro items enabling smooth Epic 3 execution.

2. **Frontend patterns need the same spec-level documentation as backend patterns** — "Existing Infrastructure to Reuse" format works; apply it to frontend patterns too.

3. **Async edge cases are a predictable bug category** — Not random. Story specs for real-time UI should include a standard checklist: stale closure guards, in-flight request cancellation, fast user action races, SignalR dedup, subscription cleanup.

4. **Deferred items need active triage, not silent accumulation** — 12 items is manageable only because they're tracked and triaged.

5. **Review process is working** — Every race condition, every accessibility issue, every edge case was caught in review. The system works; the goal is to shift detection earlier.

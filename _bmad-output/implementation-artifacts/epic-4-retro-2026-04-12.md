## Successes

1. **"Extend, don't duplicate" backend architecture** — `CreateConversationCommand` was extended with optional `ParticipantIds` and `GroupName` fields rather than creating separate group commands. The unified Conversation entity with type discriminator handled both Private and Group cleanly through the same MediatR pipeline.

2. **Story-to-story intelligence eliminated rediscovery** — Every story had "What Already Exists (DO NOT Recreate)" and "Previous Story Intelligence" sections. Story 4.4 knew to reuse the system message pattern from 4.3's `JoinGroupCommandHandler`, which was modeled on 4.2's `CreateConversationCommandHandler`. No duplication, no wasted effort.

3. **Declining review patch count (5→3→2→1)** — Clear team learning curve across the epic. Story 4.1 had 5 validation patches; by Story 4.4, only 1 patch (Observable composition). The pattern-reference sections directly drove this improvement.

4. **Strong test discipline** — +49 backend unit tests, +40 frontend tests across the epic. Every story shipped with comprehensive test coverage and zero regressions. All builds clean (0 warnings), all linting passed.

5. **Epic 3 retro follow-through (4/5 items)** — Completed items directly produced measurable results. "Existing Patterns to Reuse" treatment → declining patch count. Test failure fixes → zero regressions. Proves the retro-to-action loop works.

6. **Design token consistency** — All frontend stories reused existing `_tokens.scss` values consistently. System message pills, sender name colors, spacing, all from the established design system.

7. **Zero production incidents, zero hard blockers** — Clean execution throughout the epic.

## Challenges

1. **Validation edge cases consistently caught in review, not implementation** — Story 4.1 had 5 validation patches (duplicate IDs, no upper bound, whitespace strings, whitespace GroupName, mutual exclusion). Pattern: validators cover the happy path but miss boundary conditions.

2. **~20 deferred items accumulated** — Notably, system message real-time broadcast was deferred in ALL 4 stories. This is a systemic architectural gap, not a series of independent deferrals. Other recurring deferrals: no unique constraint on ConversationParticipant (4.3, 4.4), no pagination on queries (4.3, 4.4).

3. **Observable/subscription management bugs recurring** — Story 4.3: subscription leak in `joinGroup()` where `conversationCreated` subscription never cleaned up on error. Story 4.4: `inviteToGroup`/`leaveGroup` wrapped HttpClient in manual Observables with unretained inner subscriptions. Same bug category from Epic 3.

4. **Async edge case checklist only partially implemented** — Committed to in Epic 3 retro. Stories referenced cleanup patterns informally but no formal checklist was created. Directly correlates with recurring frontend bugs.

5. **Integration test count reporting inconsistency** — Story 4.3 reported 65 integration tests (full suite), Story 4.4 reported 41 (single file: ConversationEndpointTests.cs only). Actual total: 77. No tests lost — reporting scope was inconsistent. Resolved post-retro.

6. **Epic 4 status not updated to "done"** — Team agreement from Epic 3 retro to update status when all stories complete. Missed again.

---

## Key Insights

1. **Completed retro action items produce measurable results; partial ones leave gaps** — Proven by "Existing Patterns" sections driving patch decline, while the missing async checklist left subscription bugs unaddressed.

2. **When the same item is deferred across multiple stories, it's an architectural decision, not a deferral** — System message broadcast was punted 4 times. Needs a one-time architectural decision, not per-story deferral.

3. **"Extend, don't duplicate" is the right backend pattern** — Unified Conversation pipeline handled both Private and Group cleanly. Apply this thinking to Epic 5 (presence applies to all conversation types).

4. **Frontend patterns are maturing but need formalization** — The learning curve is real (5 patches → 1), but async edge cases need a formal checklist, not institutional memory.

5. **UI bugs need closer attention** — Project Lead flagged this as a priority. Frontend async patterns, visual state management, and subscription lifecycle are the key risk areas heading into Epic 5's UI-heavy stories.
